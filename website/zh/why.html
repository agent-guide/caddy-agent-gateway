为什么选 AgentGuide

一个控制平面，而不是又一个 Agent 框架。

LangGraph、AutoGen、CrewAI 回答的是"agent 该怎么思考？" AgentGuide 回答的是另一个问题："组织该怎么运营 agent？" —— 谁可以调用它们、它们能触碰什么、花了多少钱、如何组合成更大的能力。 一个负责造 agent，另一个负责运营 agent 资产。

本质区别

框架编排推理，AgentGuide 构建 Agent 控制平面。

框架的工作流活在单个 agent 进程内部：规划、调用工具、反思、重试。 AgentGuide 的控制在 agent 外部：今天覆盖身份、生命周期、会话、策略与归因， 下一步扩展外部任务、调度与 workflow。两者的关系就像容器运行时之于 Kubernetes —— 不同的层，缺一不可。

AgentGuide 刻意不做你框架的竞争者 —— 它是框架造出来的 agent 走向生产的地方。builtin 运行时本身就内嵌了一个 agent 框架来支撑拓扑； 而网关的职责始终不变：定义、生命周期、治理、资源与观测。

  • Builtin 运行时 内嵌框架之上的声明式 agent —— 两层可以共存的活证据。
  • ACP 运行时 Codex、OpenCode 等讲协议的 agent，以黑盒方式托管。
  • HTTP 身份 LangGraph、ADK 或自研服务今天可以注册；直接 HTTP 任务分发仍在路线图上。
  • 协议边界 ACP agent 作为受管黑盒运行；外部 HTTP agent 保留自己的实现栈。

未来的方向

从受治理的 Agent，到企业能力网络。

上面的层是为一个更大的想法打的地基：企业最终买的不是一个 agent， 而是运营一整个 agent 组织。以下是我们正在构建的抽象 —— 在路线图上，而不在今天的交付里。

vision · artifact bus

流转工作成果，而不是 prompt 链

agent 之间交换的是有版本、可审计的工件 —— PRD、架构、patch、评审 —— 而不是裸文本。每个工件都有生产者、消费者、版本与审批状态， 连成一张血缘图，一次查询就能回答"为什么失败了？"

vision · 能力组合

要结果，不点名 Agent

声明你需要的能力 —— "审这份合同"、"发布这个服务" —— 由平台决定哪些 agent 组合起来交付它，靠它们消费与产出的工件类型自动连线。

vision · agent teams

调用一支团队，而不是一个 Agent

具名团队 —— PM、架构师、编码、评审 —— 成为一等对象， 带角色路由与 supervisor 策略。今天已交付的进程内 supervisor 与 plan-execute 拓扑是第一步。

vision · 共享记忆

整个舰队的黑板

workspace 级的共享记忆，供协作中的 agent 读写 —— 比任何单个会话都长寿的上下文，和其他资源一样受治理。

从价值所在开始

控制平面从第一个 Agent 就开始回本。

不需要先有一支舰队：把一个 agent 的流量接进 AgentGuide， 第一天你就拿到归因、密钥与审批。编排层会建在一个你已经信任的地基上。
