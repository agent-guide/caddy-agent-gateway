# v0.4.x Completion Plan

## 0. About This Document

This document scopes the remaining work for the `v0.4.x` line. The goal for
`v0.4.x` is **completion, not expansion**: close correctness gaps in what
already ships, and make the docs describe the code that exists. No new
subsystems, no new dependencies, no architectural change.

Work that requires the eino upgrade, the OpenTelemetry adoption, or the eino
observability bridge belongs to `v0.5.x` and is listed in §5 only so it is not
rediscovered as a `v0.4.x` item.

Every claim below was verified against the tree at `v0.4.1-7-gc398b5b`. Each
item lists the evidence (`file:line`), the change, and the verification gate.
When this document and the code disagree, the code wins and this document is
wrong.

Conventions:

- **A** items are data-correctness defects: they make persisted rows wrong or
  unusable. Fix these first.
- **B** items are promises the docs make that the code does not keep. Either
  implement, or mark the surface as reserved.
- **C** items are hygiene and consistency.
- `go test ./...` and `go vet ./...` must pass at every item boundary.

## 1. A Disproven Assumption — Read Before Starting

`observability-implementation.md` §13 ("Remaining Exporter & Policy Hooks") and
the "Remaining Follow-Ups" section of `observability.md` both list "improve
streaming token finalization for providers that expose final usage" as remaining
work. **That item is obsolete. Delete it; do not implement against it.** Every
provider in the tree already reports streaming usage.

The eino-backed providers:

`eino-ext/libs/acl/openai@v0.1.14/chat_model.go:849` sets
`req.StreamOptions = &openai.StreamOptions{IncludeUsage: true}` unconditionally
on the streaming path. The `openai`, `deepseek`, `zhipu`, and `openrouter`
providers all route through that acl layer; the `ollama` and `gemini` eino
components return usage as well.

The three raw-HTTP providers, which are the ones a reader would expect to be the
gap, are covered too:

- `anthropic` (`pkg/llm/provider/anthropic/provider.go:98`) and `claudecode`
  (`pkg/llm/provider/claudecode/provider.go:153`) both stream through
  `anthropicbase.ReadMessageStream`, which emits a `ResponseMeta` carrying
  `Usage` at `pkg/llm/provider/anthropicbase/stream.go:164-168`.
- `codex` streams through the Responses path;
  `responsesEventStreamToMessageStream` handles `response.completed` by calling
  `responsesCompletionMessage`, which fills `ResponseMeta.Usage`
  (`pkg/llm/provider/codex/provider.go:545-556`).

The read side is in place as well: the `openai` protocol handler reads
`chunk.ResponseMeta.Usage` at `pkg/dispatcher/llmapi/openai/handler.go:355`, the
`anthropic` handler does the equivalent, and `cc` embeds `*anthropic.Handler`
(`pkg/dispatcher/llmapi/cc/handler.go:17`) and inherits that instrumentation.

Action for `v0.4.x`:

- delete the follow-up item from `observability-implementation.md` §13 and from
  the "Remaining Follow-Ups" section of `observability.md`
- add a regression test that pins the fact for the three raw-HTTP paths
  (`anthropic`, `claudecode`, `codex`), since those are the ones nothing else
  guards and the ones the stale wording kept pointing at

Verification: a test asserting a streamed `anthropic`, `claudecode`, and `codex`
response yields a non-nil `ResponseMeta.Usage` on the final chunk.

One real, narrow gap does exist and is filed as C3 below: `codex` populates only
`PromptTokens` and `CompletionTokens`.

## 2. A — Data Correctness

### A1. Admin ACP usage events carry a malformed `span_id` and no `trace_id`

Evidence:

- `pkg/admin/acp.go:483` calls `observer.Begin` with an
  `InteractionDimensions` literal that sets `RouteID`, `RouteKind`, and
  `RouteProtocol` only. `TraceID`, `SpanID`, and `ParentSpanID` are left empty.
- `internal/observability/usage/observer.go:63` then falls back to
  `dims.SpanID = uuid.NewString()`.

A W3C span id is 16 lowercase hex characters. `uuid.NewString()` produces 36
characters with hyphens. The dispatcher path is correct — `randomHex(8)` at
`pkg/dispatcher/trace.go:20` yields the right shape — so the two writers
disagree on format, and only the admin path is wrong.

Scope check: `pkg/admin/acp.go:483` is the only offending call site. All four
`observer.Begin` calls in `pkg/dispatcher/handler.go` (lines 94, 102, 120, 142)
pass `traceCtx.SpanID` explicitly, so the observer fallback never fires for
them.

Consequence: every row written through the admin ACP surface has an empty
`trace_id` and a `span_id` that no tracing system can join against. The
`idx_acp_events_trace` partial index skips them (it is
`WHERE trace_id IS NOT NULL`), so they are invisible to trace-scoped queries.

Change:

- Make the observer's fallback produce a W3C-shaped span id, not a UUID. The
  generator already exists as `randomHex` in `pkg/dispatcher/trace.go`; it
  should move to a place both callers can use rather than being duplicated.
  Land it in `internal/observability/usage` — generating a span id is the
  observer's own job, and `pkg/dispatcher/trace.go` then holds nothing but the
  W3C parser, which is exactly what `v0.5.x` deletes wholesale (§5). Do not
  create a third shared package for it.
- Give `pkg/admin/acp.go` a real trace context. An admin request has no inbound
  `traceparent`, so it should generate a fresh `trace_id` + `span_id` the same
  way the dispatcher does for an untraced request.

Verification:

- a unit test asserting the observer's generated `span_id` matches
  `^[0-9a-f]{16}$` and its `trace_id` matches `^[0-9a-f]{32}$`
- a test that an admin ACP event lands with a non-empty `trace_id`

### A2. The `traceparent` response header misreports the sampled flag

Evidence — `pkg/dispatcher/trace.go`:

- line 50: `w.Header().Set("traceparent", "00-"+tc.TraceID+"-"+tc.SpanID+"-01")`
  hardcodes trace-flags to `01` (sampled).
- lines 25-32: the inbound parser reads `parts[1]` (trace-id) and `parts[2]`
  (parent-id) but never reads `parts[3]` (trace-flags). The inbound sampled bit
  is discarded.
- line 27: `parts[0]` (version) is never validated.
- an all-zero trace-id or span-id is invalid per W3C and is accepted here.

Consequence: the gateway tells every downstream that the trace is sampled,
regardless of what the caller decided. A caller that deliberately did not sample
a request has that decision silently overridden at the gateway boundary.

Change:

- parse trace-flags from the inbound `traceparent` and propagate the sampled bit
  through `traceContext` into `writeTraceHeaders`
- reject a malformed version byte, a non-hex trace-id/span-id, and the all-zero
  forms, falling back to generating a fresh trace context

Note: `v0.5.x` replaces this hand-rolled parser with
`propagation.TraceContext{}`. Fix it anyway — `v0.4.x` should not ship a
header that lies, and the fix is small. Keep it self-contained so `v0.5.x` can
delete the file rather than untangle it.

Verification:

- table test over the W3C traceparent test vectors: valid sampled, valid
  unsampled, bad version, all-zero trace-id, all-zero span-id, short field
- an assertion that an inbound unsampled `traceparent` produces an unsampled
  outbound `traceparent`

### A3. `usage_finalized` has a wrong SQL default

Evidence: `pkg/configstore/sqlite/usage_schema.go:30` declares
`usage_finalized INTEGER NOT NULL DEFAULT 1`.

The default encodes "token counts are trustworthy" for a row that did not say
so. Every current writer passes the column explicitly
(`pkg/configstore/sqlite/usage_writer.go:23`), so nothing is wrong today. This
is a latent trap: the first writer added without that column will silently mark
unfinalized usage as finalized, and the resulting rows are indistinguishable
from real ones.

Change: drop the default entirely — `usage_finalized INTEGER NOT NULL`. A
writer that omits the column then fails its `INSERT` loudly instead of taking
any default at all. `DEFAULT 0` was the obvious candidate but it only converts
a silent wrong answer into a silent right-looking answer; the point of the item
is that no writer should ever omit this column.

Two limits on what this buys, both of which must be stated plainly rather than
left for a reader to discover:

- The tables are created with `CREATE TABLE IF NOT EXISTS`, so the new
  declaration applies to newly created databases only. **Every already-deployed
  database keeps `DEFAULT 1` and keeps the trap.** No migration is required and
  no stored value changes, but the trap is narrowed, not eliminated.
- Because of that, the schema change alone does not guard the tree. Pair it with
  a test that asserts the column set `usage_writer.go` writes matches the column
  set `usage_schema.go` declares, for each of the three event tables. That test
  catches the omitted-column writer on every database, old or new, and is the
  part of this item that actually holds.

Verification:

- a test that inserts a row without `usage_finalized` against a freshly created
  table and asserts the `INSERT` fails
- a test asserting writer columns and schema columns agree for
  `llm_usage_events`, `mcp_usage_events`, and `acp_usage_events`

## 3. B — Promises The Code Does Not Keep

### B1. The MCP tool-policy columns are never populated

Evidence:

- `pkg/configstore/sqlite/usage_schema.go:44` creates `presented_tool_name`,
  `executed_tool_name`, `execution_mode`, and `policy_action`.
- `internal/observability/usage/observer.go:231` copies them from
  `MCPExtension` onto the event, and `usage_writer.go` persists them.
- **No code anywhere calls `SetExtension` with any of these four fields set.**
  A repository-wide search across `pkg/dispatcher/` and `pkg/mcp/` returns
  nothing.

The four columns are therefore always `NULL`. The read path and the query
allowlists expose them as if they were real dimensions.

Change for `v0.4.x`: **document them as reserved, do not implement the policy.**
Implementing MCP tool policy (`docs/design/mcp-tool-policy.md`) is a feature,
not a completion, and it does not belong in this line. Add a comment at the
schema declaration and a sentence in `observability.md` stating that these
columns are created for a future policy layer and are unpopulated in `v0.4.x`,
so downstream consumers do not query them expecting values. The relevant
section is "10.2 MCP Usage Events Table".

Verification: none beyond review — this item is a documentation change.

### B2. ACP context-token metrics do not exist

Evidence: `ContextUsedTokens`, `ContextWindowTokens`, `TokenDelta`, and
`UsageObserved` appear nowhere in `internal/observability/usage/event.go`. The
entire §9.1 plan in `observability-implementation.md` is unimplemented.

The raw ACP usage payload *is* captured — `ACPExtension.UsageJSON`
(`event.go:131`), populated by `wrapACPEventSinkForUsage`
(`pkg/dispatcher/acp_handler.go:173`) — so no data is lost. It is stored as an
opaque blob and is not queryable or aggregatable.

Change for `v0.4.x`: none. The work involves new event fields, a SQLite
migration, a per-session last-value tracker with bounded eviction, and a
Prometheus counter change. That is a feature.

What `v0.4.x` *does* owe: `observability-implementation.md` §9.1 and the
"Remaining Follow-Ups" section of `observability.md` currently read as a plan
of record. Mark them explicitly
as **not implemented in v0.4.x, deferred to v0.5.x**, and note that `usage_json`
holds the raw payload in the meantime.

### B3. The `OpenTelemetrySink` seam has no exporter

`internal/observability/pipeline/otel_sink.go` is reachable only from
`export_sink_test.go:40`. Deferred to `v0.5.x`, where it is subsumed by real
OTel adoption. The misleading "deployment-supplied" wording has already been
corrected; no further `v0.4.x` action.

## 5. Explicitly Deferred To v0.5.x

Listed so they are not rediscovered as `v0.4.x` work.

- upgrade eino to latest; prefer eino's provider implementations and keep local
  implementations only where eino does not suffice
- adopt the `go.opentelemetry.io/otel` API in the gateway core. The dependency
  is already linked: `go mod why go.opentelemetry.io/otel/trace` resolves
  through `caddy/modules/standard` → `caddyhttp/tracing`. It is `// indirect`
  in `go.mod` only.
- replace `pkg/dispatcher/trace.go` with `propagation.TraceContext{}`
- outbound traceparent injection via a `traceRoundTripper` in
  `pkg/httpclient.BuildHTTPClient`. Note that `httpclient.go:101` wraps
  `headerRoundTripper` only when `len(headers) > 0`; the trace round tripper
  must wrap unconditionally. The precondition — that `ctx` reaches the outbound
  `http.RoundTripper` on every provider path — was verified out of tree with a
  throwaway probe and holds.
- child spans per `executeWithFallback` attempt
  (`pkg/gateway/routedprovider.go:224`), which today makes retries, credential
  fallbacks, and model fallbacks invisible — only the final attempt reaches
  the single usage event
- an eino `callbacks.Handler` bridging eino component spans onto the gateway
  span. Two facts make the bridge viable, both verified out of tree: eino fires
  global callback handlers on bare `Generate`/`Stream` calls, outside a
  `compose.Graph`; and it surfaces streaming token usage through
  `OnEndWithStreamOutput`. Two hazards, also verified:
  - `callbacks.AppendGlobalHandlers` appends to process-wide state and has no
    unregister counterpart. A Caddy `reload` re-runs app provision and would
    register a second handler, double-counting tokens. Guard with `sync.Once`.
  - `OnEndWithStreamOutput` hands the handler a *copy* of the stream, drained on
    a separate goroutine. The protocol handler meanwhile calls `span.Finish()`,
    which is idempotent and first-call-wins. Streaming usage from eino can
    therefore arrive after the span has closed and be dropped. This race needs a
    design answer before the bridge is written.
- eino callbacks cover only the six eino-backed providers. `anthropic`,
  `claudecode`, and `codex` are raw HTTP and fire no callbacks, so the bridge
  can enrich but cannot serve as the trace backbone.
- ACP context-token metrics (B2)
- MCP tool policy (B1)
- an OTLP exporter replacing the `OpenTelemetrySink` seam (B3)
